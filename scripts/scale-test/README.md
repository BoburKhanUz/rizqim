# RIZQIM "one big database" load test kit

The kit writes only into its own gitignored `logs/`, `results/` and `cache/` folders; configuration is environment
variables only (`env.sh`), `backend/.env` is never edited. `cache/` holds Laravel's config cache with the secrets of
`backend/.env`: delete it after a run. Run it on a dev box or staging, never against production data. The results of
the first run (2026-11-14) and their analysis are in `docs/scale/`.
Needs: Postgres 16 with `pg_stat_statements` (+ `auto_explain`) in `shared_preload_libraries`, PHP 8.3 (pdo_pgsql, redis,
opcache), `redis-server`, Node 22, `pgbench`, `sudo -n -u postgres psql`.

| file | what |
|---|---|
| `env.sh` | all env for artisan/server: `DB_DATABASE` (default `scale_big`), `SCALE_WORK` (where `logs/`, `results/`, `cache/` go; default this folder), `QUEUE_CONNECTION=null`, `BROADCAST_CONNECTION=null` (Reverb off), `CACHE_STORE=redis` on the kit's own redis `SCALE_REDIS_PORT` (16379; `server.sh start` flushes it, so two runs on one machine need different ports) (rate limiters/locks as in prod), mail array, Telegram/FCM/SMS creds empty, outbound HTTP black-holed (`http(s)_proxy=127.0.0.1:9`), logs to stderr, opcache + config/route/event cache in `cache/` |
| `server.sh start [workers] / stop` | (stop: only what the kit started: pid files in `cache/pids` checked against the command line, nginx/php-fpm by their pid files in `cache/fpm`, the kit's Redis by its port; never another stack's Reverb or queue worker) redis + `php artisan serve` with `PHP_CLI_SERVER_WORKERS` on `$APP_PORT` (18500) |
| `SERVER=fpm ./server.sh start` (or `SERVER=fpm ./run.sh ...`) | fpm mode: nginx + php-fpm (`apt-get install nginx php8.3-fpm`) with the repo's real `backend/docker/nginx.conf`, `php-fpm.conf` and `pools.sh` (pools critical / market / default / analytics, the routing map, the market and analytics limits); only paths and ports are rewritten, into `cache/fpm/`. Sizes and limits: the `FPM_*` / `NGINX_*` env of `pools.sh` (its defaults when unset; `[workers]` is ignored); pool ports `FPM_PORT_BASE` (19000) +0/+1/+2/+3. Logs: `logs/php-fpm-access.log` (each request with its pool name), `logs/nginx-error.log` (limit hits), `logs/nginx-access.log`. Re-measuring L3 against it: `SERVER=fpm ./run.sh L load` |
| `PROF=cpu\|1 SERVER=fpm ./server.sh start` | profiler (`php/prof/`, fpm mode only, as php-fpm's `auto_prepend_file`): `cpu` logs each request's CPU time (getrusage) and wall time into `$PROF_LOG` (`logs/prof.jsonl`); `1` serves it through an instrumented `public/index.php` and also logs phases, each service provider's register+boot, every SQL statement and autoloaded classes; `PROF_TL=1` adds the container-resolution timeline, `PROF_OC=1` OPcache status, `PROF_CLASSES=<file>` the declared classes (input of `php/prof/preload-list.php`, which writes `backend/docker/preload-classes.txt`). Summary: `php php/prof/report.php logs/prof.jsonl [--providers] [--sql]`. Other fpm knobs: `FPM_KIT_INI=0` (only the image's `php.ini`, not `php/zz-scale-opcache.ini`), `FPM_EXTRA_INI_DIR=<dir>` (try a setting), `EVENT_CACHE=0`. Results: `docs/scale/PHP_COST_M2.md` |
| `pgbouncer.sh start / stop / stats` | PgBouncer (transaction mode, `apt-get install pgbouncer`) on `$DB_POOL_PORT` (16432), configured by `infra/pgbouncer/entrypoint.sh` like the compose service; `DB_POOLER=pgbouncer ./server.sh start` (or `./run.sh`) then sends the app through it, as php-fpm in production (`env.sh`: `DB_POOLER`, default `direct` = the first run) |
| split roles (optional; `docs/scale/RESULTS_M4.md`) | export `DB_PORT` (default 5432; the app, PgBouncer and the kit's superuser `psql` use it), `DB_USERNAME`/`DB_PASSWORD` (application login), `DB_OWNER_USERNAME`/`DB_OWNER_PASSWORD` (owner: `base.sh` then migrates as it and runs `scripts/db-roles.sh`), `DB_TENANT_ROLE` and `TENANT_RLS=0\|1` before `base.sh` / `m2.sh`; `scale_rt` becomes a member of that application login with its BYPASSRLS. After an `m2.sh` run delete `cache/*.php` before `base.sh`: the config cache left behind points artisan at the stopped PgBouncer |
| `base.sh` | fresh `$DB_DATABASE`: migrate, `PosStackSeeder`, ONE real POS order and ONE Mini App order through the API (`template_order.mjs`), `sql/templates.sql` copies their row shapes; keeps `${DB_DATABASE}_tmp` as a copy |
| `sql/gen.sql` | generator, append mode: `-v g1 -v g2 -v days`; a group = 20 market-only + 1 POS-only + 2 hybrid stores with menus, staff, tills/KDS/display, stations, hall+15 tables, 1 500 customers, closed shifts, 30 days of orders with every row a real order writes. FKs stay enforced (no replica mode), so the load itself proves FK integrity |
| `sql/mint.sql` | tokens by SQL, hashed like Sanctum (`sha256(plain)`, client sends `id|plain`): till device + cashier PIN-session (+ the `staff.session_started` audit row), KDS cook session, display device, owner, customers -> JSON on stdout |
| `sql/sizes.sql` | VACUUM ANALYZE, top tables/indexes, MEASURED bytes/order per channel |
| `sql/indexes.sql` | the index experiment (create / drop statements) |
| `load.mjs` | the driver: scenarios `lunch`, `poll`, `reports`, `market` (with spike window), `sync`, `hub`, `probe`; per-endpoint p50/p95/p99, errors, CPU seconds of php/postgres (from /proc), pg_stat_database deltas, pg_stat_activity samples, pg_stat_statements top lists (`--pgss 1`) |
| `load.mjs` M2 client modes (switches; without them the driver is the M1 client) | `"client":{"cond":true,"unconditional_s":110,"refresh":"ws"\|"sim"}` with `poll`: every screen keeps its last `ETag` per URL and sends `If-None-Match` (a 304 keeps the body), the Flutter screens send one poll without it when the poll time since the last full read reaches `unconditional_s` (60 s polls: every 2nd, 15 s: every 8th), the owner board (browser) never; `refresh:"ws"` opens one real Pusher-protocol socket per screen to Reverb (Node 22 `WebSocket`, `POST /api/broadcasting/auth`, `pusher:ping`) and re-reads once per channel event (debounced 300 ms, skipped when the event's `rev` equals the token the screen read, re-read on a heartbeat whose `rev` differs), `"sim"` = one event per POS order write to every screen of the branch instead (no sockets); poll intervals `till_s`/`kds_s`/`display_s`/`web_s` (live 60/15/30/60, fallback 15/15/5/15). `"market":{...,"mode":"m2","orders_s":60,"notif_s":15,"avail_s":20,"scroll_pct":30}`: the M2 Mini App (fixed address per customer, `catalog?view=cards&limit=50` + `stores?page=1&per_page=10` when older than react-query's staleTime 30/60 s, more pages on scroll, store menu by uuid + `catalog/availability`, background `notifications`/`orders?scope=active` polls, every GET with `If-None-Match`). `"probe304":{"reps":40}`: one client, each polled GET `reps` times without and `reps` times with `If-None-Match`: statements, PHP/Postgres/PgBouncer/Redis CPU ms per request and p50 of a 200 vs a 304. New outputs: per endpoint 304 share and body bytes, CPU of `redis`, `reverb`, `queue`, `scheduler` (php processes split by command line; `php` stays the web processes), Redis commands/s, statements by DB role, socket/event counters |
| `load.mjs` M2 fix round 2 client (`"client":{...,"rules":"paced","till":"alt"\|"stack","refresh":"ws"}`, the `m2b` presets) | the clients after the "lunch storm" fix (commits e1bf367, bdb8736, 81d11f8; see the comment block `b3)` in `load.mjs` for the rules and the files they come from). Flutter screens (till floor, open order page, KDS, display) keep R (proven by a read), S (accounted for) and doubt per screen, feed EVERY event into S, read only on their relevant events, and pace those reads (leading + trailing throttle: KDS 2 s / 0-0.5 s, floor 5 s / 0-1.5 s, order page 1 s / 0-0.3 s, display 0.3 s / 0-0.25 s); a heartbeat reads when its `rev` is not S (or doubt, not on the display). The owner board reads `GET /staff/orders/{uuid}` per relevant event (3 s / 0-1 s, > 5 uuids: one open-list read), applies kitchen events from the payload, reads the open list on a gap or heartbeat ahead (30 s / 0-5 s), safety-polls `GET /staff/orders?scope=active` every `web_s` and never `?status=new`. Polls are not paced: till 60 s and display 30 s periodic, KDS 15 s after its last read. `till`: `alt` = the m1/m2 driver's till (the floor does not read while an order is open), `stack` = the app's navigation (the floor stays mounted under the order page and reads at once when it closes). `pacing` overrides `{kds,floor,order,display,board_order,board_list:[window_ms,spread_ms]}`. Needs real sockets (`RT=1`; `refresh:"sim"` is not supported). New outputs: `realtime.reads_by_kind` (reads per screen and cause, heartbeat verdicts, dropped due reads), `asked` / `skipped_asked` / `ignored` / `dropped` / `heartbeat_asks` / `retries` / `return_reads`; `probe304` now also covers `GET /staff/orders?scope=active` and `GET /staff/orders/{uuid}` and reports `body_bytes` |
| `RT=1 ./server.sh start` (fpm mode) | real-time on: `BROADCAST_CONNECTION=reverb`, queue on the kit's Redis, plus `php artisan reverb:start` on `REVERB_PORT` (18580), one `queue:work --queue=default,broadcasts` and `php/rt/heartbeat.php` (queues the scheduler's 30 s `SendRealtimeHeartbeat` only; `RT_SCHEDULER=full` runs `schedule:work`). Those three connect straight to Postgres as role `scale_rt` (member of the app role, own config cache `cache/config-rt.php`), so their statements and backend CPU are split out; `./server.sh drop-rt-role` removes the role. Throwaway local Reverb key/secret, `no_proxy=127.0.0.1` so the app reaches Reverb's HTTP API |
| `m2.sh <label> <preset\|cfg>` | one M2 run in the shipped mode (fpm + PgBouncer), PgBouncer and server restarted per run (Redis flushed), waits for load < 1.0, writes `<label>.txt/.json/.pgss.txt/.fpm.txt/.pgbouncer.txt/.redis.txt`. Presets: `m1-L1`, `m1-L3`, `m1-L4` (M1 client), `m2-L1`, `m2-L3`, `m2-L4` (M2 client; run with `RT=1`; `REFRESH=sim` for simulated events), `m2-L1-down` (M2 client at the fallback intervals, no events: real-time down; `RT=0`), `m2b-L1`, `m2b-L3`, `m2b-P` (fix round 2 clients; `RT=1`; `TILL=stack` for the app's navigation), `probe304`. `DB_DATABASE` defaults to `scale_m2` there |
| `logstats.mjs`, `m2summary.mjs` | php-fpm access log (`server.sh` adds `cpu=%{total}C`) + nginx access log -> per endpoint and status: count, 304 share, wall and PHP CPU ms, wire bytes, kB per POS store per minute; result JSONs -> the tables of `docs/scale/RESULTS_M2.md` |
| `pgbench/*.sql` | DB-only: Mini App poll, till poll, top-products report, one POS order's writes (rolled back) |
| `run.sh <S|M|L> [phases]` | end to end: `base gen mint probe load pgbench` |

Reproduce: `./run.sh S` (≈5 min), `./run.sh M gen mint probe`, `./run.sh L gen mint probe load pgbench` (≈45 min).
On staging: run the same with the real compose stack instead of `server.sh` (set `APP_PORT` to nginx), php-fpm
`pm.max_children` tuned, and a bigger `days`/group count (Server-90d profile = ~60 groups x 90 days).
M2 measurement (2026-11-17, `docs/scale/RESULTS_M2.md`): `DB_DATABASE=scale_m2 ./run.sh L base gen mint`, then
`./m2.sh L1_m1mode m1-L1`, `RT=1 ./m2.sh L1_m2 m2-L1`, `./m2.sh L1_down m2-L1-down`, ... and `node m2summary.mjs results/*.json`.
Clean up: `./server.sh stop; ./server.sh drop-rt-role; sudo -u postgres psql -c 'drop database scale_big' -c 'drop database scale_tmp'; rm -rf cache` (with your own
`DB_DATABASE` / `SCALE_WORK`: those names). Two runs side by side: give each its own `SCALE_WORK`, `SCALE_REDIS_PORT`, `APP_PORT`,
`FPM_PORT_BASE`, `DB_POOL_PORT` + `PGB_DIR` and `DB_DATABASE`.
